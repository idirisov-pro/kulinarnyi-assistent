# P0: первичная проверка вариантов центрального хранилища

Дата: 2026-09-04
Статус: первичная проверка; окончательный поставщик не выбран

## 1. Правило выбора

Ни один вариант не считается подходящим только потому, что у него есть бесплатный тариф или простая библиотека JavaScript.

Для «Кулинарного ассистента» важны одновременно:

- доступность из целевых стран;
- возможность держать секреты только на сервере;
- защита от массовых поддельных запросов;
- возможность хранить сырые события и отзывы;
- экспорт и удаление данных;
- предсказуемые ограничения тарифа;
- отсутствие влияния сбоя аналитики на основную функцию приложения.

## 2. Cloudflare Workers + D1 + Turnstile

### Подтверждено официальной документацией

- Workers Free имеет бесплатный объём запросов.
- D1 доступен на бесплатном тарифе и имеет отдельные дневные лимиты чтения, записи и общий лимит хранения.
- При достижении бесплатных дневных лимитов D1 запросы начинают возвращать ошибки до сброса лимита; неожидательного автоматического списания на бесплатном тарифе из этого не следует.
- Turnstile имеет бесплатный тариф и может использоваться независимо от других сервисов Cloudflare.

### Критический риск

Cloudflare официально сообщает о систематическом ограничении трафика к сервисам, защищённым Cloudflare, со стороны российских интернет-провайдеров. По состоянию на официальную справку 2026 года это может делать такие сервисы непригодными или нестабильными для пользователей внутри России.

### Вывод

Для продукта, который должен надёжно работать в России, Cloudflare нельзя выбирать как единственный центральный узел без реального теста доступности на целевых российских сетях.

Для аудитории вне России вариант технически остаётся сильным, но это не отменяет географического риска.

## 3. Supabase

### Подтверждено официальной документацией

- есть бесплатный тариф;
- бесплатный проект включает PostgreSQL, API и ограниченный объём вызовов Edge Functions;
- публичный ключ допустимо использовать в браузере только вместе с корректно настроенными правами и Row Level Security;
- секретный/service-role ключ нельзя размещать в клиентском JavaScript;
- бесплатные проекты могут приостанавливаться после периода бездействия;
- официальная документация отдельно предупреждает о рисках региональных блокировок многоарендной инфраструктуры.

### Риски

- требуется аккуратная настройка прав доступа;
- открытая запись для анонимного пользователя без дополнительной защиты создаёт риск спама;
- для безопасной приёмки отзывов предпочтительнее серверная функция, а не прямая запись из браузера;
- приостановка бесплатного проекта после бездействия неудобна для нерегулярных бета-тестов;
- нет подтверждения, что доступ будет одинаково стабильным во всех целевых странах.

### Вывод

Supabase остаётся реальным кандидатом для бета-теста, но его нельзя объявить выбранным без проверки доступности из целевых сетей и без прототипа защиты публичной формы.

## 4. Firebase

### Подтверждено официальной документацией

Firebase имеет бесплатный тариф Spark для части сервисов; Analytics предоставляется без отдельной платы. Однако доступность серверных функций и отдельных облачных сервисов зависит от выбранного тарифа и продукта.

### Риски

- экосистема заметно шире, чем требуется маленькому P0;
- часть серверных возможностей может потребовать перехода на тариф с биллингом;
- использование только Firebase Analytics не решает задачу хранения свободного текста обратной связи;
- требуется отдельно проверять правила доступа к базе и фактические квоты конкретной связки.

### Вывод

Не исключается, но пока не имеет явного преимущества над более простыми вариантами для текущей задачи.

## 5. Промежуточное решение

На этой точке нет достаточного основания выбрать одного поставщика как окончательное решение.

Поэтому клиентскую часть нужно строить независимо от поставщика:

- один модуль регистрации событий;
- одна очередь событий;
- один интерфейс отправки;
- адрес приёмника задаётся конфигурацией тестовой сборки;
- смена поставщика не должна требовать переписывания продуктовой логики.

До включения сетевой отправки в публичную версию нужно провести два практических теста:

1. доступность выбранного приёмника из реально целевых сетей/стран;
2. устойчивость к поддельным и массовым запросам.

## 6. Что делать дальше

1. Реализовать независимый клиентский модуль событий без привязки к поставщику.
2. Подключить его к ключевым действиям приложения в отдельной ветке.
3. Не включать передачу событий наружу по умолчанию, пока не выбран и не проверен центральный приёмник.
4. После выбора приёмника добавить тестовую сетевую конфигурацию и обновить политику конфиденциальности.
5. Только после успешной проверки объединять изменения с `main`.
