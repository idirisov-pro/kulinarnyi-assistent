# P0: аналитика, обратная связь и решение по Telegram

Дата: 2026-09-04
Статус: proposal for validation

## 1. Цель

До дальнейшего масштабирования продвижения получить измеримый ответ на три вопроса:

1. Пользователь понимает ценность продукта и доходит до первого подбора?
2. Каталог и алгоритм дают достаточно полезный результат для реальных продуктовых наборов?
3. Возвращается ли пользователь повторно без ручного напоминания?

До получения этих данных широкое продвижение и платное привлечение не являются приоритетом.

## 2. Что считаем фактами текущей версии

- Публичная сборка: `3.1-beta.1`.
- Приложение — статическое PWA на GitHub Pages.
- Сервер, регистрация и централизованная база данных отсутствуют.
- Автоматической сетевой продуктовой аналитики нет.
- Текущий каталог содержит 23 рецепта: 10 со статусом `reviewed`, 13 со статусом `draft`.
- `reviewed` означает редакционную проверку, а не подтверждённое фактическое приготовление.
- Обратная связь формируется в приложении, после чего пользователь должен поделиться ею через системное меню или вручную вставить скопированный текст.

## 3. Главный риск измеримости

Сейчас невозможно надёжно измерить полный продуктовый funnel:

`visit -> start -> ingredients -> search -> results -> recipe -> cooking -> completion -> feedback -> return`

Поэтому отдельные показатели соцсетей нельзя использовать как доказательство качества самого продукта.

## 4. Минимальный набор событий P0

### Обязательные события

- `session_started`
- `ingredient_added`
- `ingredient_removed`
- `search_submitted`
- `results_shown`
- `zero_results`
- `recipe_opened`
- `cooking_started`
- `cooking_completed`
- `feedback_submitted`
- `session_returned`

### Параметры, которые действительно нужны

- анонимный `install_id` или иной псевдонимный идентификатор;
- `session_id`;
- версия продукта;
- источник перехода / campaign tag;
- число выбранных продуктов;
- выбранное время;
- число порций;
- режим подбора;
- число точных результатов;
- число близких результатов;
- id открытого рецепта;
- длительность этапов funnel;
- факт возврата.

Не собирать без отдельной необходимости имя, телефон, email и содержимое личных сообщений.

## 5. Основные метрики P0

### Activation

Доля новых пользователей, которые дошли до `results_shown`.

### Result success

Доля поисков, где есть хотя бы один точный результат.

### Recipe intent

Доля `results_shown`, закончившихся `recipe_opened`.

### Cooking intent

Доля `recipe_opened`, закончившихся `cooking_started`.

### Completion

Доля `cooking_started`, закончившихся `cooking_completed`.

### Retention

Возврат пользователя в отдельную новую сессию.

### Feedback capture

Доля активных сессий, из которых реально получен централизованный отзыв.

## 6. Telegram: три возможные модели

### A. Только чат-бот

Пользователь пишет продукты текстом, затем порции и получает рецепты сообщениями.

Плюсы:
- низкий порог входа;
- не требуется отдельная установка приложения;
- естественный канал повторного контакта после того, как пользователь сам начал диалог;
- можно централизованно получать события и отзывы.

Минусы:
- ввод большого набора продуктов в чате быстро становится неудобным;
- исправление, удаление и просмотр текущего содержимого кухни хуже, чем в интерфейсе с кнопками;
- выдача нескольких рецептов и фильтров перегружает чат;
- сам Telegram не решает проблему маленького каталога.

Вердикт: не рекомендуется как единственный интерфейс.

### B. Только Telegram Mini App

Текущий HTML/JS интерфейс переносится внутрь Telegram Mini App.

Плюсы:
- можно переиспользовать значительную часть текущего интерфейса;
- удобный выбор продуктов, порций и параметров;
- запуск из Telegram в один-два действия;
- Telegram предоставляет контекст пользователя после подтверждения;
- можно связать Mini App с ботом для уведомлений, обратной связи и повторных сценариев.

Минусы:
- всё равно нужен backend для безопасного хранения bot token, централизованной аналитики и состояния между устройствами;
- появляется зависимость от Telegram как платформы.

Вердикт: технически сильнее чистого чат-бота.

### C. Гибрид: Bot + Mini App

Рекомендуемая гипотеза.

- Бот = вход, повторный контакт, короткие команды, feedback, сообщения после приготовления.
- Mini App = ввод продуктов, порций, фильтров, просмотр результатов и рецепта.
- Backend = аналитика, пользовательское состояние, feedback, каталог/версии.

Вердикт: лучший кандидат на ограниченный validation test.

## 7. Предлагаемый Telegram core loop

1. Пользователь открывает бота по deep link.
2. Нажимает `Подобрать ужин`.
3. Открывается Mini App.
4. Первый запуск: пользователь создаёт `Мою кухню` из основных продуктов.
5. Следующие запуски: меняет только то, что добавилось/закончилось.
6. Указывает время и порции.
7. Получает 2–3 лучших варианта, а не длинный каталог.
8. Открывает один рецепт и нажимает `Начать готовить`.
9. После ожидаемого времени бот может запросить короткую оценку, только если пользователь уже дал боту право на сообщения.
10. Feedback сохраняется централизованно.

## 8. Что Telegram не исправляет

Переход в Telegram сам по себе не решает:

- покрытие каталога;
- качество рецептов;
- доверие к результатам;
- плохое ранжирование;
- слабое позиционирование;
- отсутствие повторной ценности.

Если те же 23 рецепта просто перенести в чат, продукт останется ограниченным, только в другом интерфейсе.

## 9. Validation gate перед полноценной миграцией

Не делать полный rewrite сразу.

Сначала построить тонкий Telegram prototype и сравнить два входа на одной продуктовой логике:

### Контроль

`social / direct -> web PWA`

### Тест

`social / direct -> Telegram bot -> Mini App`

Сравнивать:

- start -> first search;
- first search -> usable result;
- result -> recipe open;
- recipe -> cooking start;
- feedback rate;
- повторный запуск.

Главный вопрос эксперимента: снижает ли Telegram трение и увеличивает ли повторное использование, а не просто количество открытий.

## 10. Архитектурное решение на текущей точке

### Принять

- P0 instrumentation до следующего серьёзного acquisition test.
- Централизованный feedback вместо копирования текста пользователем.
- Telegram Bot + Mini App как приоритетную гипотезу канала/оболочки для validation.

### Не принимать пока

- полный отказ от web/PWA;
- полный перенос продукта в чистый чат-бот;
- платную подписку;
- масштабное продвижение Telegram-версии;
- обещание AI-функций, которых нет в продукте.

## 11. Следующий технический шаг

Сделать отдельный технический прототип, не затрагивая стабильную публичную ветку:

1. Telegram bot shell.
2. Mini App wrapper над текущим core UI.
3. Минимальный backend endpoint для событий и feedback.
4. Event schema из раздела 4.
5. Deep-link attribution.
6. Экран согласия/объяснения минимального сбора данных.
7. Тест на ограниченной группе реальных пользователей.

После этого принять решение `continue / pivot / stop` по данным, а не по субъективной привлекательности интерфейса.
