# P0: измеримость продукта, обратная связь и отдельная проверка Telegram

Дата: 2026-09-04
Статус: решение после повторной критической проверки

## 1. Цель

До дальнейшего масштабирования продвижения получить измеримый ответ на три продуктовых вопроса:

1. Пользователь понимает ценность «Кулинарного ассистента» и доходит до первого подбора?
2. Каталог и алгоритм дают достаточно полезный результат для реальных наборов продуктов?
3. Возвращается ли пользователь повторно без ручного напоминания?

До получения этих данных широкое продвижение и платное привлечение не являются приоритетом.

## 2. Проверенные факты о текущей версии

Источник фактов — актуальная ветка `main` репозитория на дату документа.

- Публичная сборка: `3.1-beta.1`.
- Приложение — статическое PWA на GitHub Pages.
- Сервер, регистрация и централизованная база данных отсутствуют.
- Автоматической сетевой продуктовой аналитики нет.
- Текущий каталог содержит 23 рецепта: 10 со статусом `reviewed`, 13 со статусом `draft`.
- `reviewed` означает редакционную проверку, а не подтверждённое фактическое приготовление.
- Обратная связь формируется в приложении, после чего пользователь должен поделиться ею через системное меню или вручную вставить скопированный текст.

Эти факты не доказывают ни наличие, ни отсутствие рыночного спроса. Они лишь описывают текущую техническую и контентную базу.

## 3. Проверенный вывод: главный блокирующий фактор — отсутствие измеримости

Сейчас невозможно надёжно измерить полный путь пользователя:

`посещение -> начало работы -> выбор продуктов -> запуск подбора -> результаты -> открытие рецепта -> начало приготовления -> завершение -> отзыв -> повторный визит`

Следовательно:

- показатели соцсетей нельзя использовать как доказательство качества продукта;
- переход на другую платформу сам по себе не решит проблему измеримости;
- прежде чем сравнивать веб-версию и Telegram, нужна единая система событий и единый способ собирать обратную связь.

## 4. Обязательный следующий этап: измеримость текущего веб-приложения

### События, которые нужно регистрировать

Технические идентификаторы событий в коде могут оставаться английскими, если это упрощает разработку, но пользовательская документация и интерфейс должны быть на русском языке.

Минимальный набор:

- начало нового сеанса;
- добавление продукта;
- удаление продукта;
- запуск подбора;
- показ результатов;
- отсутствие результатов;
- открытие рецепта;
- начало приготовления;
- завершение приготовления;
- отправка отзыва;
- повторный визит.

### Параметры, которые действительно нужны

- псевдонимный идентификатор установки или браузера;
- идентификатор сеанса;
- версия приложения;
- источник перехода и метка кампании, если они есть;
- число выбранных продуктов;
- выбранное время;
- число порций;
- режим подбора;
- число точных результатов;
- число близких результатов;
- идентификатор открытого рецепта;
- длительность ключевых этапов;
- факт повторного визита.

Без отдельной необходимости не собирать имя, телефон, электронную почту, содержимое личных сообщений и другие данные, не нужные для проверки продукта.

## 5. Метрики, которые можно рассчитывать после внедрения событий

Здесь намеренно не задаются численные пороги успеха без фактической базовой линии.

Нужно измерять:

- долю новых пользователей, дошедших до первого подбора;
- долю подборов, где найден хотя бы один точный результат;
- долю показов результатов, после которых открыт рецепт;
- долю открытых рецептов, после которых начато приготовление;
- долю начатых приготовлений, отмеченных как завершённые;
- долю сеансов, из которых реально получена обратная связь;
- повторные визиты пользователей.

Пороговые значения для решений `продолжать / менять / останавливать` должны определяться после получения исходных данных, а не назначаться заранее из предположений.

## 6. Централизованная обратная связь — отдельная обязательная задача

Текущая схема «сформировать текст -> поделиться -> выбрать способ отправки» создаёт лишнее трение и не гарантирует, что разработчик реально получит отзыв.

Требование P0:

- пользователь нажимает «Отправить отзыв»;
- приложение подтверждает успешное сохранение;
- отзыв попадает в единое хранилище;
- отзыв связан с версией приложения, сеансом и контекстом подбора;
- пользователь видит, какие данные отправляются;
- личные данные не добавляются автоматически без необходимости.

Выбор конкретного сервиса или серверной технологии в этом документе не фиксируется: сначала нужно проверить доступные варианты, стоимость, ограничения, приватность и совместимость с текущей архитектурой.

## 7. Telegram: что подтверждено, а что остаётся гипотезой

### Подтверждено технически

Telegram поддерживает ботов и Mini Apps. Mini App может использовать полноценный HTML-интерфейс внутри Telegram.

### Не подтверждено данными нашего продукта

У нас пока нет оснований утверждать, что Telegram:

- даст более высокую долю завершённых подборов;
- уменьшит время до первого полезного результата;
- повысит повторное использование;
- улучшит сбор отзывов настолько, чтобы оправдать зависимость от платформы;
- будет удобнее прямой веб-ссылки для пользователей, пришедших из Instagram, VK или других внешних источников.

Поэтому Telegram нельзя считать выбранной архитектурой продукта.

## 8. Три гипотезы интерфейса для будущего сравнения

### A. Текущая веб-версия

Преимущества:

- открывается по обычной ссылке;
- не требует Telegram;
- сохраняет независимость от одной платформы;
- уже существует и может стать базовой линией для измерений.

Риски:

- текущий первый экран перегружен;
- повторный возврат зависит от того, вспомнит ли пользователь о сервисе;
- без серверной части нет централизованной аналитики и обратной связи.

### B. Простой Telegram-бот со свободным вводом

Гипотеза:

Пользователь пишет одной фразой, например:

`курица, картофель, яйца, сыр; 3 порции; 40 минут`

и получает несколько вариантов.

Возможное преимущество — минимальное количество действий, если распознавание текста работает надёжно.

Риски:

- длинные списки трудно редактировать;
- сложнее видеть текущее содержимое «Моей кухни»;
- выдача нескольких рецептов и настроек может перегружать чат;
- нужен достаточно надёжный разбор свободного текста.

Статус: гипотеза, не отвергать заранее и не объявлять победителем.

### C. Telegram-бот + Mini App

Гипотеза:

- бот используется как точка входа и канал повторного взаимодействия;
- Mini App используется для выбора продуктов, порций и просмотра рецептов;
- серверная часть хранит события и обратную связь.

Возможное преимущество — удобное сочетание чата и графического интерфейса.

Риски:

- дополнительный переход из внешних площадок в Telegram может увеличить трение;
- появляется зависимость от Telegram;
- требуется серверная часть и проверка данных Telegram;
- перенос интерфейса не решает проблему маленького каталога и качества рецептов.

Статус: перспективная, но недоказанная гипотеза.

## 9. Почему Telegram не является следующим техническим шагом

Ранее предлагалось сразу строить Telegram-прототип. После повторной проверки это решение отклонено как преждевременное.

Причины:

1. Проблему аналитики можно и нужно решить в текущем веб-приложении.
2. Проблему централизованной обратной связи также можно решить без Telegram.
3. При 23 рецептах плохой результат в Telegram будет невозможно однозначно объяснить: причина может быть в платформе, интерфейсе, каталоге, алгоритме или самих рецептах.
4. Без базовой линии веб-версии сравнение платформ будет слабым и методологически грязным.

## 10. Проверка покрытия каталога — параллельная задача P0

Нужно сформировать набор реальных бытовых ситуаций и проверять для каждой:

- найден ли хотя бы один точный вариант;
- найден ли близкий вариант;
- какие продукты предлагается докупить;
- реалистично ли время;
- корректно ли пересчитываются порции;
- соответствует ли рецепт заявленным продуктам;
- вызывает ли результат доверие;
- можно ли реально приготовить блюдо по инструкции.

Не устанавливать заранее искусственный порог вроде «80% корзин должны срабатывать», пока нет базовой линии и понимания состава тестового набора.

## 11. Новый порядок работ

### P0-A. Измеримость веб-версии

Добавить регистрацию ключевых событий и источников перехода.

### P0-B. Централизованная обратная связь

Сделать прямое сохранение отзыва без обязательного ручного копирования и пересылки.

### P0-C. Проверка покрытия каталога

Проверить реальные наборы продуктов и зафиксировать причины неудачных подборов.

### P1. Исправление основных причин плохой выдачи

Работать по фактическим данным P0, а не по предположениям.

### P2. Упрощение первого использования

Сократить путь до полезного результата, если данные подтвердят лишнее трение.

### P3. Сравнительный эксперимент с Telegram

Только после появления базовой линии сравнить:

1. веб-версию;
2. простой Telegram-бот со свободным вводом;
3. Telegram-бот + Mini App.

Использовать одинаковую рецептурную базу и одинаковую логику подбора.

### P4. Решение о платформе

Выбирать основную оболочку только по поведению реальных пользователей и качеству результата.

## 12. Что принимается сейчас

- измеримость текущего веб-приложения — обязательный следующий технический этап;
- централизованная обратная связь — обязательный следующий технический этап;
- проверка покрытия каталога — обязательная параллельная задача;
- текущая веб-версия остаётся базовой линией;
- Telegram остаётся отдельной гипотезой для последующего сравнительного эксперимента.

## 13. Что сейчас не принимается

- полный отказ от веб-версии;
- перенос продукта в Telegram до получения базовой линии;
- утверждение, что Telegram эффективнее веб-приложения;
- утверждение, что Mini App эффективнее простого бота;
- платная подписка;
- масштабное платное продвижение;
- численные цели и прогнозы без основания;
- обещание функций, которых в продукте нет.

## 14. Ближайший технический шаг

Перед изменением публичной ветки подготовить отдельную ветку реализации P0 и выполнить:

1. схему регистрации событий веб-версии;
2. единый модуль отправки событий с безопасным отказом при недоступности сервера;
3. выбор и проверку конкретного способа централизованного хранения событий и отзывов;
4. прямую отправку формы обратной связи;
5. обновление политики конфиденциальности под фактически собираемые данные;
6. проверку на тестовой версии;
7. только после этого — предложение на объединение с `main`.

Telegram-прототип в этот этап не входит.
