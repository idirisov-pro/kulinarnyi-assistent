# P0: план внедрения измеримости веб-версии

Дата: 2026-09-04
Статус: рабочий план реализации

## 1. Цель

Подготовить текущую веб-версию «Кулинарного ассистента» к контролируемым пользовательским тестам так, чтобы можно было измерить путь пользователя и централизованно получить обратную связь.

Этот документ не выбирает Telegram и не меняет продуктовую платформу.

## 2. Что должно быть готово до объединения изменений в `main`

### 2.1. Регистрация событий

Минимально фиксировать:

1. начало сеанса;
2. добавление продукта;
3. удаление продукта;
4. запуск подбора;
5. показ результатов;
6. отсутствие результатов;
7. открытие рецепта;
8. начало приготовления;
9. завершение приготовления;
10. отправку отзыва;
11. повторный визит.

### 2.2. Источник перехода

Сохранять только технически необходимую информацию:

- `utm_source`, если передан;
- `utm_medium`, если передан;
- `utm_campaign`, если передан;
- реферер верхнего уровня, если доступен и нужен для проверки источника.

Не записывать полный адрес страницы-источника, если в нём могут находиться лишние параметры или персональные данные.

### 2.3. Идентификаторы

Нужны два псевдонимных идентификатора:

- идентификатор установки/браузера;
- идентификатор текущего сеанса.

Не использовать имя пользователя, номер телефона, электронную почту или аккаунт социальной сети как идентификатор аналитики.

### 2.4. Централизованная обратная связь

Форма отзыва должна отправлять данные напрямую в выбранное хранилище.

Минимальный состав:

- версия приложения;
- идентификатор сеанса;
- тип отзыва;
- оценка, если пользователь её указал;
- фактическое время, если указано;
- текст проблемы/наблюдения;
- готов ли пользователь использовать сервис снова;
- контекст последнего подбора: число продуктов, время, порции, число результатов, открытый рецепт;
- источник перехода, если он известен.

### 2.5. Поведение при ошибке сети

Если сервер аналитики недоступен:

- приложение не должно ломаться;
- событие можно временно сохранить локально и повторить отправку позже;
- пользователю нельзя показывать техническую ошибку аналитики как ошибку подбора рецептов.

Если не отправился отзыв:

- пользователь должен получить явное сообщение, что отзыв не сохранён;
- допустим резервный вариант «Скопировать текст отзыва», но он не должен считаться успешной централизованной отправкой.

## 3. Что нельзя делать

- Не отправлять содержимое всех локальных данных пользователя целиком.
- Не отправлять историю браузера.
- Не собирать полный текст поисковых запросов вне задачи подбора продуктов.
- Не добавлять сторонние рекламные идентификаторы.
- Не считать событие успешно отправленным, если оно осталось только в локальном хранилище.
- Не задавать произвольные численные показатели успеха до получения базовой линии.

## 4. Архитектура клиентской части

Добавить один независимый модуль регистрации событий, чтобы продуктовая логика не зависела от конкретного сервиса аналитики.

Интерфейс модуля должен поддерживать как минимум:

- `startSession()`;
- `track(eventName, properties)`;
- `identifySource()`;
- `submitFeedback(payload)`;
- локальную очередь при временной недоступности сервера.

Конкретные технические имена функций могут отличаться, если сохраняется эта ответственность модуля.

## 5. Выбор центрального хранилища

До внедрения сетевой отправки нужно отдельно проверить минимум четыре аспекта каждого кандидата:

1. работает ли он с текущим статическим приложением;
2. как защищается запись от массового спама и поддельных запросов;
3. какие данные и где хранятся;
4. есть ли обязательные расходы или жёсткие ограничения бесплатного режима.

Нельзя выбирать сервис только потому, что его проще подключить.

## 6. Проверка перед публикацией

На тестовой ветке воспроизвести минимум следующие сценарии:

- первый визит без UTM-меток;
- визит с UTM-метками;
- добавление и удаление продукта;
- успешный подбор;
- нулевая выдача;
- открытие рецепта;
- начало и завершение приготовления;
- успешная отправка отзыва;
- отказ центрального сервиса;
- повторный визит на том же устройстве.

Для каждого сценария проверить не только наличие события, но и отсутствие лишних данных.

## 7. Критерий готовности P0-A/P0-B

Этап считается технически готовым только когда:

- события реально поступают в централизованное хранилище;
- отзыв реально сохраняется без ручной пересылки пользователем;
- при отказе аналитики основное приложение продолжает работать;
- политика конфиденциальности соответствует фактически отправляемым данным;
- тестовая ветка прошла ручную проверку перечисленных сценариев.

До выполнения этих условий широкое привлечение пользователей не возобновлять.
