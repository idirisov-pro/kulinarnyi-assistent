# P0 — пробный серверный приёмник событий

Статус: технический прототип. Не развёрнут. Не подключён к публичной версии.

## Зачем он нужен

Приёмник предназначен только для продуктовых событий P0. Он не является системой хранения текстовых отзывов и не должен использоваться для `feedback_submitted` до появления отдельного подтверждённого механизма сохранения обратной связи.

Цепочка:

`веб-приложение -> HTTPS POST -> Yandex Cloud Function -> YDB`

## Что проверяет сервер

Сервер не доверяет клиентской проверке и повторно проверяет:

- наличие массива `events`;
- размер партии не более 50 событий — это соответствует текущему размеру клиентской партии;
- допустимое имя события;
- формат идентификаторов события, установки и сеанса;
- корректность времени события;
- ограничение глубины и размера пользовательских свойств;
- допустимый `Origin` для обычного браузерного запроса.

`Origin` не является аутентификацией: вне браузера его можно подделать или не передать. Это только дополнительный фильтр для обычного браузерного трафика.

## Идемпотентность

`event_id` используется как первичный ключ YDB. Повторная доставка той же партии приводит к `UPSERT`, поэтому повтор события с тем же `event_id` не создаёт новую строку.

Если запись партии оборвалась после частичного сохранения, клиент получает ошибку и позже может повторить всю партию. Уже сохранённые события будут перезаписаны по тому же ключу, а недостающие — добавлены.

## Хранение

Таблица создаётся запросом из `schema.sql`.

Для пробного варианта весь нормализованный объект события дополнительно сохраняется в `payload_json`, а ключевые поля вынесены в отдельные столбцы. Время хранится как ISO-строка `Utf8`, чтобы на этапе P0 не вводить лишнюю зависимость от преобразований типов времени между клиентом и SDK.

## Переменные окружения

Обязательные для функции:

- `YDB_CONNECTION_STRING` — полный адрес подключения YDB, включая `?database=...`;
- `YDB_METADATA_CREDENTIALS=1` — использовать учётные данные сервисного аккаунта через сервис метаданных;
- `KA_P0_ALLOWED_ORIGINS` — допустимые источники через запятую, например `https://idirisov-pro.github.io`.

Необязательная:

- `KA_P0_EVENTS_TABLE` — имя таблицы, по умолчанию `p0_events`.

Сервисному аккаунту функции нужно выдать только права, необходимые для записи в выбранную YDB, а не административные права на облако.

## Версия Node.js и SDK

Прототип рассчитан на Node.js 22. Зависимости YDB закреплены в `package.json` на конкретных версиях и отдельно импортируются в CI.

Используется современный модульный JavaScript SDK YDB (`@ydbjs/core`, `@ydbjs/query`, `@ydbjs/auth`) с параметризованными запросами. Это снижает риск SQL/YQL-инъекций по сравнению со сборкой запроса из пользовательских строк.

## Что намеренно не используется

### Cloud Logging как основное хранилище

Не используется. По актуальной документации Yandex Cloud сервис Cloud Logging планируется закрыть во II квартале 2027 года в пользу Monium. Логи функции могут использоваться только для диагностики, но не как каноническое хранилище событий продукта.

### Старое ограничение частоты API Gateway

Расширения `x-yc-apigateway-rate-limits` и `x-yc-apigateway-rate-limit` больше не считаются действующим решением: актуальная документация Yandex Cloud помечает их как устаревшие и рекомендует Smart Web Security.

Для P0 сначала используются строгая схема, ограничение партии, идемпотентность и контроль источника. Если реальный трафик потребует дополнительной защиты, её нужно выбирать отдельно и проверять по действующей документации на момент развёртывания.

## Что ещё не доказано

До настоящего развёртывания нельзя считать подтверждёнными:

- успешную авторизацию функции в конкретной YDB пользователя;
- сетевую доступность из целевых стран и сетей;
- реальные задержки и стоимость;
- поведение под нагрузкой;
- достаточность защиты публичного приёмника;
- корректность политики конфиденциальности для фактического набора собираемых полей.

Поэтому адрес приёмника нельзя включать в публичной версии до отдельного испытания и обновления пользовательской информации о сборе данных.
